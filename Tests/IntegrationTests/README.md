# Интеграционные тесты

Требуют локального Supabase (`supabase start`), поэтому вынесены из пакетов
и не входят в `swift test` по умолчанию.

Обязательный тест этапа 0 — изоляция RLS (SPEC §3.2): два анонимных клиента,
проход по всем таблицам, проверка что второй не видит ни одной строки первого.
Без него схема считается непринятой.

`rls_isolation.sh` — этот тест на прямом SQL-уровне (через
`set local role authenticated; set local request.jwt.claims = ...`, тем же
механизмом, что описывает §20.4). Требует `supabase start` из
`Supabase/migrations/` и `enable_anonymous_sign_ins = true` в
`Supabase/config.toml`. Не заменяет будущий HTTP-тест 20a (§20.15) — тот
пойдёт через реальные эндпоинты `Server`, когда пакет появится.

```
Supabase/migrations$ supabase start
Tests/IntegrationTests$ ./rls_isolation.sh
```

## Локальная база под тесты сервера

Сервер ходит в Postgres не владельцем, а ролью `fitserver` без собственных прав
(§20.4, миграция `0008`). Пароля в миграции нет — он конфигурация среды, — и
задавать его нужно **после каждого** `supabase db reset`:

```
psql "$SUPABASE_DB_URL" -c "alter role fitserver password 'fitserver';"
```

Каждый раз, а не один: `db reset` удаляет кастомные роли вместе с базой, и
`0008` создаёт `fitserver` заново — уже без пароля. Идемпотентность самой
миграции этим прогоном поэтому НЕ проверяется; чтобы её проверить, файл нужно
применить дважды подряд к базе, где роль уже есть.

`Auth/` принимает только ES256 и RS256 (§20.5), а локальный проект по умолчанию
подписывает легаси-секретом HS256, и тогда ни один выписанный им токен проверку
не проходит. Поэтому `config.toml` включает асимметричные ключи:

```
Supabase$ supabase gen signing-key --algorithm ES256 > signing_keys.json
```

Файл в `.gitignore` и на каждой машине свой; `signing_keys_path` в `config.toml`
уже указывает на него. После этого `/auth/v1/.well-known/jwks.json` отдаёт
настоящий ES256-ключ, а токены анонимных пользователей им подписаны — это то,
что нужно тестам 20k и 20b.
