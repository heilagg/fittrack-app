# Implement Feature (FitTrack)

Процедура для одного модуля за раз: прочитать контекст → проверить зависимости
→ ветка → реализация по уже утверждённой архитектуре → тесты на каждый
сценарий §18 → коммит. Отработана на `FitCore/Equipment/WeightLadder`,
следующий модуль по этой же процедуре — `FitCore/Progression`.

Модуль — не обязательно весь SPM-таргет: это может быть один подмодуль внутри
`FitCore` (`Equipment`, `Progression`, `Recovery`, `Cycle`, `Readiness`,
`Planner`) или отдельный пакет (`FitContent`, `FitData`). Каждая итерация
скилла закрывает ровно один такой модуль.

## 1. Прочитать контекст, а не изобретать заново

Архитектура уже зафиксирована — не в отдельном файле, а в doc-комментарии
модуля, написанном на этапе скелета (коммит "Add project skeleton"). Он
описывает конвейер, ключевые типы и то, какие сценарии §18 модуль обязан
закрыть. Например `Packages/FitCore/Sources/FitCore/Progression/Progression.swift`
уже говорит:

- два слоя реакции — `nextSet(...)` внутри сессии и `betweenSessions` между
  сессиями;
- центральная функция — `rebuildStates(from:)`, состояние как свёртка над
  журналом подходов;
- демпфирование baseline живёт только в `BaselineUpdater`.

Прочитать перед началом работы:

1. Doc-комментарий модуля целиком (`.../<Module>/<Module>.swift`).
2. Соответствующий раздел SPEC.md — по номеру, на который ссылается
   комментарий (например §9 для Progression). Не только сам раздел, но и
   псевдокод в нём: он обычно фиксирует сигнатуры функций.
3. SPEC §18 — какие пронумерованные сценарии относятся к этому модулю
   (Progression = 1–14, Cycle = 15–26, Planner = 27–33, Sync = 34–37). Часть
   могла уже закрыться предыдущим модулем — сверить с его doc-комментарием
   (`WeightLadder` закрыл 1–3, 14 из "прогрессии", Progression'у остаются
   4–13).
4. Уже реализованные соседние модули, от которых этот зависит — их публичный
   API, а не только их doc-комментарии.

## 2. Проверить порядок зависимостей раньше, чем ветку

`FitCore` — zero-dependency: сам он не зависит ни от `FitContent`, ни от
`FitData`, ни от SwiftUI/SwiftData/`Foundation.Date`. Внутри `FitCore`
подмодули зависят друг от друга не хаотично:

```
Types (растёт по мере необходимости)
  └─ Equipment/WeightLadder         ✅
        └─ Progression   §9    — нужен Equipment (nextAchievableWeight, roundToAchievable)
  Recovery  §8   — независим, нужен только Types
  Cycle     §11  — независим, нужен только Types
        └─ Readiness §10 — нужен Cycle (PhasePolicy/confidence)
  Planner   §7   — нужен Equipment + Recovery + Cycle/Readiness + состояние Progression
```

`FitContent` и `FitData` зависят от `FitCore`, не наоборот — их можно вести
параллельно, они не блокируют работу внутри `FitCore`.

Перед тем как начинать модуль, свериться: все модули слева от него в графе
уже реализованы? Если нет — либо сначала реализовать их, либо явно сказать
пользователю, что выбранный модуль требует чего-то ещё не готового, и
предложить более раннюю по графу альтернативу.

## 3. Ветка

```bash
git checkout -b feature/<module-in-kebab-case>
```

Имя — по модулю, не по тикету: `feature/weight-ladder`, `feature/progression`,
`feature/recovery`. Ветка от `master`, если рабочее дерево чистое (`git
status` перед этим — обязательно).

## 4. Реализовать по уже утверждённой архитектуре

- Схема и структура типов — те, что зафиксированы doc-комментарием модуля и
  §3.1 SPEC.md (Postgres-схема), а не придуманные заново. Если у типа из
  Postgres нужен только срез полей (как `EquipmentProfile` — не весь
  `equipment_profiles`, а только то, что влияет на лестницу весов) — брать
  ровно тот срез, что нужен этому модулю, с комментарием почему остальное не
  нужно здесь.
- Не трогать другие модули без необходимости. Исключение — файлы, которые
  сама архитектура называет общим домом для типа (`Types.swift` явно
  перечисляет, что должно жить в нём: `MuscleSlug`, `Pattern`, `LoadType`,
  `Feedback`, `Phase`, `Goal`, `ExperienceLevel`, `ReasonCode`,
  `CalendarDay`/`Timestamp`). Добавлять туда минимально — только то, что
  прямо нужно текущему модулю для компиляции, а не весь список сразу.
- `swiftSettings: [.swiftLanguageMode(.v6)]`, никакого `Foundation.Date` в
  бизнес-логике (только собственные `CalendarDay`/`Timestamp` из `Types`) —
  тесты фаз цикла и детренированности иначе плывут от часового пояса и DST.
- После реализации — `swift build` в пакете, должен проходить чисто.

## 5. Обязательные тесты — по одному на каждый сценарий §18

Каждый сценарий из SPEC §18, который doc-комментарий модуля называет
закрытым этим модулем, — отдельный тест с номером сценария в имени функции
или в комментарии над ней (`test_scenario7_...` или `// Сценарий 7: ...`).
Так проверяется на глаз: все ли заявленные сценарии реально покрыты, не
потерялся ли один при рефакторинге.

Плюс — тесты на контракт, который не входит в номерной список §18, но на
который сценарии опираются (например построение лестницы для каждого
`loadType` отдельно от того, что тестируют сами 4 сценария). Их помечать
отдельным `// MARK:`, чтобы не путать с обязательными.

Не покрывать тестами то, что явно принадлежит другому, ещё не реализованному
модулю (пример: `WeightLadder` не решает "расширить диапазон или прыгнуть на
вес" — это Progression; тест на `WeightLadder` проверяет только сам
достижимый вес, а не реакцию на процент шага).

**Framework:** в этом окружении установлены только Command Line Tools —
ни `XCTest`, ни `Testing` не собираются (`swift test` падает на
`no such module`). Писать тесты на `XCTest` (стандартный выбор без лишних
SPM-зависимостей), но не пытаться прогнать их здесь через `swift test`.
Вместо этого — временный `.executableTarget`, слинкованный с проверяемым
пакетом, с теми же утверждениями через `assert`/`print`+`exit(1)`, прогнать
через `swift run`, затем удалить сам таргет и файлы, и убедиться, что
`git status`/`git diff Package.swift` снова чистые перед коммитом. Это не
замена тестам — только способ убедиться, что логика верна, раз
`swift test` здесь не работает; сами тесты (`XCTest`) всё равно идут в
коммит и должны быть готовы выполниться в CI/Xcode на машине пользователя.

## 6. Коммит

Один коммит на модуль (если пользователь явно не просит дробить), в стиле
двух предыдущих (`Add project skeleton...`, `Implement FitCore/Equipment:
WeightLadder`):

- **Заголовок** — императив, английский, `Implement <Package>/<Module>:
  <ключевой тип>` (например `Implement FitCore/Progression: BaselineUpdater`).
- **Тело** — тоже английский, объясняет **нетривиальные решения**, а не
  пересказывает диff построчно:
  - какие сценарии §18 закрыты и почему остальные — нет;
  - решения, где SPEC.md неполон или неоднозначен, и какой выбор сделан и
    почему (не молча — явно, отдельным абзацем);
  - что сознательно отложено и на какой будущий модуль это ляжет;
  - если тесты писались через обходной путь (см. §5 про CLT-only
    окружение) — сказать это явно, а не полагаться на то, что читатель
    коммита это восстановит.

## 7. Несостыковки со SPEC.md — фиксировать, не чинить

Если по ходу реализации SPEC.md противоречит сам себе, что-то не описывает
(например какой источник инкремента веса у `bodyweight_loaded`) или
описывает вещь, для которой нет данных в схеме Postgres (например у
`machine_step_kg` нет верхней границы стека) — **не редактировать SPEC.md**.
Задокументировать находку в теле коммита отдельным блоком и явно назвать в
ответе пользователю после реализации. Решение по неоднозначности — сделать
разумный, задокументированный выбор в коде (с пометкой в комментарии, что
это выбор, а не факт из спеки), а не молча выбрать один вариант и не
угадывать без пометки.

## Итоговый чек-лист перед тем, как считать модуль готовым

- [ ] Doc-комментарий модуля и соответствующий раздел SPEC.md прочитаны.
- [ ] Зависимости модуля (по графу выше) уже реализованы.
- [ ] Ветка `feature/<module>` создана от чистого `master`.
- [ ] Код следует уже зафиксированной архитектуре; другие модули не
      затронуты без необходимости.
- [ ] `swift build` проходит чисто.
- [ ] На каждый заявленный сценарий §18 — отдельный тест с номером сценария
      в имени/комментарии.
- [ ] Логика прогнана вручную (временный executable), если `swift test`
      здесь не собирается; временные файлы удалены, `git status` чист.
- [ ] Коммит: императив, английский заголовок, тело с обоснованием
      нетривиальных решений.
- [ ] Несостыковки со SPEC.md зафиксированы в коммите и озвучены
      пользователю — SPEC.md не редактировался.
