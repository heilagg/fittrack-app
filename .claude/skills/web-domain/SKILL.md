# Web Domain (FitTrack)

Веб-клиент отличается от всех модулей, сделанных до него, тремя вещами, и
каждая меняет процедуру:

1. **Это не Swift.** `implement-feature` написана про SPM-пакеты FitCore,
   FitContent, FitData; `server-domain` — про Vapor. `Web/` — единственная часть
   репозитория со своим менеджером пакетов (npm) и своим жизненным циклом
   сборки (§20.2). Ни `swift build`, ни `swift test` его не проверяют.
2. **У него нет доменной логики, и заводить её нельзя.** Всё, что считается —
   вес, готовность, фаза, состав тренировки, причина пересборки — приходит с
   сервера готовым. Единственное исключение — применение дерева §20.9, и оно
   тоже не вычисление, а чтение готовой карты состояний.
3. **Его контракт — чужой.** Форма границы `/v1` описана в `Packages/FitAPI` на
   Swift, а клиент пишет вторую копию руками (§6 ниже). Расхождение не падает
   само: оно проявляется пустым экраном посреди тренировки.

## 1. Что такое веб-клиент по SPEC

Полная замена телефону, а не компаньон (§20.1): онбординг, план, тренировка,
цикл, растяжка, прогресс, профиль, экспорт и удаление. Различие с iOS ровно
одно, принципиальное: **офлайна нет** (§20.10).

Система из трёх частей: веб-фронтенд (экраны, ввод, кеш контента), Swift-сервер
(собирает вход FitCore, зовёт его, пишет домен), Supabase (Postgres + Auth +
RLS). FitCore в браузер не компилируется и не переписывается ни целиком, ни
частично, ни «маленьким куском §9.3» (§20.1).

### Три вещи, которые клиент делает сам

1. **Ходит в `/v1/*`** с JWT в `Authorization: Bearer`. В каждом запросе, где
   день имеет значение, шлёт локальную дату и IANA-зону (§20.7).
2. **Пишет напрямую в Supabase шесть таблиц** (§20.6): `equipment_profiles`,
   `user_restrictions`, `parq_responses`, `cycle_events`, `daily_checkins`,
   `body_weight_entries`. Остальные доменные таблицы, включая `profiles` и
   `cycle_profiles`, пишет только сервер.
3. **Применяет дерево решений §20.9** мгновенно, без запроса на каждый тап по
   кнопке фидбэка, и отправляет факт подхода отдельным запросом.

Больше клиент ничего не решает.

### Ограничения (§20.10, §20.12, §20.14)

- **Без сети экран тренировки не работает.** Очереди незаписанных подходов нет
  ни в памяти, ни в `localStorage`; обрыв показывается прямо и немедленно, а не
  прячется за оптимистичным UI. Повтор после таймаута — это второе нажатие
  кнопки, и сервер к нему готов (идемпотентность, §5 ниже).
- **Мобильный макет — основной** (375–430 px); десктоп получает тот же макет в
  колонке ограниченной ширины. Широкой вёрстки в MVP нет.
- **Требования §13.2 переносятся буквально:** одна главная цифра, ввод тапами по
  «−»/«+», четыре кнопки фидбэка во всю ширину высотой 64, флаг боли отдельно и
  никогда в одном ряду с «тяжело».
- **Экран не гаснет** — Screen Wake Lock API, запрашивается на входе в
  тренировку и отпускается на выходе.
- **Таймер считается от абсолютной метки времени**, а не тиками: свёрнутая
  вкладка в iOS Safari замораживает таймеры. Сигнал — звук и вибрация; Live
  Activity на вебе не эмулируется.
- **PWA-манифест без service worker.** Офлайн-кеша нет.
- **Уведомления §13.6 на вебе не реализуются.**
- **Тон** (§13.5) и формулировки про цикл (§14.6) действуют без изменений.
- Чего веб не делает: офлайн, HealthKit, Live Activity, Web Push; не пишет
  `sets` иначе как через сервер и не считает §9.3 сам (§20.14).

## 2. Стек и структура `Web/` (принято)

Vite + React + TypeScript — по SPEC (§2). Остальное принято пользователем:

| Что | Выбор |
|---|---|
| Роутинг | React Router |
| Серверное состояние | TanStack Query (в том числе кеш `/v1/content/*` по `ETag`) |
| Auth и прямые записи | `@supabase/supabase-js` |
| Стили | CSS-переменные из общего источника токенов, без UI-кита |
| Юнит-тесты | Vitest + Testing Library |
| Сквозные тесты | Playwright против локальных Supabase и Server |
| Менеджер пакетов | npm |

```
Web/
  package.json, vite.config.ts, tsconfig.json, index.html
  public/                  # manifest.webmanifest, иконки
  src/
    api/        # клиент /v1: fetch, date+tz, конверт ошибки, типы и схемы
    auth/       # supabase-js, анонимный вход, линковка, токен для api/
    direct/     # записи в шесть таблиц (RLS) и вызов /rebuild после них
    content/    # кеш /v1/content/* по ETag
    features/   # onboarding, today, workout, profile (stretching, progress — В3)
    ui/         # компоненты
    app/        # роутинг, провайдеры
  e2e/          # Playwright
Tools/design-tokens/       # источник токенов и генератор (см. §8)
```

SPA раздаётся с того же origin, что и API (§20.13): CORS не нужен. В разработке
Vite проксирует `/v1` на сервер (по умолчанию `:8080`); Supabase клиент
вызывает напрямую по его адресу.

## 3. Правила работы

### 3.1 `date` и `tz` в каждом запросе, где день имеет значение (§20.7)

- Локальная дата `YYYY-MM-DD` и IANA-зона (`Intl.DateTimeFormat().resolvedOptions().timeZone`)
  идут в query у `GET`-путей и в тело у `POST`/`PATCH`. Исключение одно:
  `PATCH /v1/profile` — профиль не содержит ни одной величины, привязанной ко
  дню.
- Пара берётся из одного места в `api/`, а не собирается на экранах: две копии
  расходятся ровно на полуночи.
- Сервер сравнивает присланное с своими часами и отклоняет расхождение больше
  суток (`date_skew`, 422). Клиент это показывает, а не подменяет дату.
- Путь `/preview` — единственный с двумя датами: `date`/`tz` — «сегодня»
  клиента, `day` — дата среза внутри `week_start`.

### 3.2 Идентификатор подхода — до отправки (§20.6, тест 20e)

- UUID подхода (`crypto.randomUUID()`) создаётся во фронтенде **до** отправки
  `POST …/sets` и едет в теле. Сервер делает upsert по нему.
- Повтор после таймаута шлётся **с тем же `id`**. Новый `id` на повторе — это
  второй подход.
- Тело без `id` — `set_id_required`, 422; сервер `id` сам не выдаёт.
- `prescribed_kg` в теле приходит от клиента (вес назначило дерево), а
  `prescribed_reps` — нет.
- Завершённый подход иммутабелен (`set_immutable`, 409).

### 3.3 Прямые записи и `/rebuild` (§20.3, §20.6)

- Шесть таблиц пишутся из `direct/` через supabase-js под JWT пользователя;
  политики §3.2 действуют буквально. `updated_at` у них нет, конфликтовать
  нечем.
- После правки `equipment_profiles` клиент зовёт
  `POST /v1/week-plans/{week_start}/rebuild` с причиной `equipment_changed`;
  после нового `cycle_events` — с `cycle_event_added`. **Других причин сервер не
  принимает**: остальное он наблюдает сам.
- Ответ `/rebuild` несёт `notice` — строку «План обновлён» (§7.1). Её нужно
  показать. Молчаливая пересборка запрещена.
- Профиль инвентаря «по умолчанию» — строка с `is_default = true`. Без неё
  профиль неполон (`is_complete = false`, генерация — `profile_incomplete`,
  `details.missing` называет `equipment_profile`).

### 3.4 Дерево §20.9 на клиенте

- Дерево — **карта состояний**: `start`, `nodes`, у узла `weight_kg`,
  `truncated`, `terminates`, `transitions`. Переход ведёт к идентификатору узла,
  а не к вложенному потомку.
- Клиент по фидбэку и повторам выбирает ветку, показывает вес следующего
  подхода и **отправляет факт отдельным запросом**. Ответ `POST …/sets` — новое
  дерево (`{decision_tree}`), а не готовый следующий подход.
- `terminates` — досрочное завершение упражнения (§9.3).
- `truncated` — дальше дерева нет, идти на сервер.
- **Что уводит состояние с дерева и требует запроса:** флаг боли, ручная правка
  веса или повторов за пределы предикатов ветки, замена упражнения, пропуск
  подхода. Угадывать нельзя.
- Изменение рекомендации показывается явно: «68 кг → 62 кг» с короткой причиной
  (§13.2).
- Упражнения без веса получают дерево без весов — только ветка досрочного
  завершения.
- Ветвление в клиенте — только по готовой карте. Формул §9.3 (×0.90, ×0.95,
  ×1.05, ×1.15) в коде фронтенда быть не должно.

### 3.5 Без очереди и офлайна

- Нет `localStorage`/IndexedDB-очереди, нет service worker, нет оптимистичных
  записей, которые не подтвердил сервер.
- `localStorage` допустим только под удобства одного зрителя (последняя вкладка,
  свёрнутый блок), всегда в `try/catch`, и экран обязан работать без него.
  Сессия supabase-js лежит там же (§4.2), но это не наше хранилище.
- Ошибка сети на экране тренировки — явное состояние с кнопкой повтора, а не
  тихий ретрай в фоне.

### 3.6 Ошибки и причины

- Успех — голое тело без конверта; ветка успех/ошибка берётся из HTTP-статуса.
  Ошибка — `{error: {code, message, details}}`.
- Ветвится клиент по `code` из закрытого словаря §20.3, `details` пользователю не
  показывает никогда, `message` показывает по умолчанию.
- Различимое поведение: `unlinked_account` → экран линковки; `profile_incomplete`
  → возврат в онбординг на экран, вычисленный по `details.missing`;
  `date_skew` → сообщение о часах; `jwks_unavailable` (503) → повторить, а не
  разлогинивать; `unauthorized` (401) → заново войти.
- Причины `{code, params, message}`: у любой причины фазового происхождения в
  `params` лежит `cycle_confidence`, и клиент обязан им воспользоваться —
  предъявить рекомендацию тем осторожнее, чем он ниже (§14.6). `message` от этой
  обязанности не освобождает.
- Форма разбирается одним куском кода на все причины: размеченное объединение
  по `code`.

### 3.7 Линковка и вход (§20.5)

- Анонимный вход с первого экрана; онбординг и PAR-Q проходятся анонимно.
- «Начать тренировку» требует привязанного аккаунта: сервер на
  `POST /v1/workouts` отдаёт `unlinked_account` (403) — это экран линковки, а не
  «forbidden».
- Единственный способ завести аккаунт — email magic link. Apple позже и только
  как `linkIdentity`.
- Привязка идёт через `auth.updateUser({email})`, а не `signInWithOtp`: так
  `auth.uid()` остаётся тем же, а `signInWithOtp` завёл бы второго пользователя
  и оставил историю на первом. Письмо уходит, только если в проекте включено
  подтверждение email (`enable_confirmations = true`); при `false` Supabase
  привязывает адрес мгновенно и без письма, и любой мог бы занять чужой
  адрес. **Локально это настроено в `Supabase/config.toml`, а в продакшен-
  проекте Supabase настройку надо включить вручную** (Authentication →
  Providers → Email → Confirm email): конфиг репозитория на облачный проект не
  действует, и без неё магической ссылки не будет.
- Сервер сам отказывает анониму на `POST /v1/workouts` (`unlinked_account`,
  403, до разбора тела); профиль, инвентарь и генерация недели анониму
  доступны.
- Занятый адрес и вход в существующий аккаунт на другом устройстве SPEC не
  описывает (§19.2 п. 22): клиент показывает текст ошибки Supabase как есть.
- `/v1/content/*` публичные: токен не нужен и на них не шлётся.

### 3.8 Контент

- `GET /v1/content/exercises` и `/stretches` — с `ETag`, долгий кеш на клиенте;
  до этапа В3 растяжки — пустой список (валидный ответ).
- По проводу едет срез показа из семи полей: `slug`, `name`, `cues`,
  `common_errors`, `illustration`, `default_rest_seconds`, `equipment_labels`
  (подписи снаряда §6.6; разделитель ставит клиент). Шаг «+»/«−» берётся
  из инвентаря пользователя, а не из разметки.
- До появления картинок `illustration` — заглушка `placeholder/<тип дня>/<слаг>`
  (§6.5); клиент рисует заглушку, а не пустое место.
- Слаг, которого нет в кеше контента, — не повод падать: показывается слаг и
  логируется, а кеш перезапрашивается.

### 3.9 Таймер отдыха (§13.3)

- Длительность — `default_rest_seconds` × множитель по `weight_readiness`
  упражнения: ниже 0.9 — ×1.2, выше 1.05 — ×0.8, иначе ×1.0. Границы строгие.
- Фидбэк «тяжело» — +30 с. Кнопки «+30 сек» и «Пропустить».
- Конец — абсолютная метка времени; за 10 секунд и по окончании — вибрация и
  звук. Таймер не блокирует интерфейс.

## 4. Что известно про состояния профиля и недели

Клиент различает их по данным, а не по догадке:

- `GET /v1/profile`: незаполненное — `null`; `is_complete` — ответ сервера
  (четыре поля `profiles` **и** инвентарь по умолчанию). Правило клиент у себя
  не воспроизводит.
- «С какого экрана продолжать онбординг» вычисляется из недостающего, а не
  хранится счётчиком шагов (§5).
- `GET /v1/today` не отказывает на неполном профиле: `day.kind = not_built`,
  `session = null`, `day_id = null`. `cause = null` — недели нет; `cause`
  `not_a_training_day` — обычный день отдыха. Показывать их нужно по-разному.
- `POST /v1/week-plans` идемпотентен: те же параметры → 200 и та же неделя;
  другие параметры на ту же неделю → `week_exists`, 409.
- `POST /v1/workouts` идемпотентен по `planned_day_id`: первый старт 201, повтор
  200 и та же тренировка; другой `equipment_profile_id` на повторе →
  `day_not_planned`, `details` несёт `id` идущей тренировки.
- `POST …/finish` повторно — 200 и то же тело; `week.notice` в повторе `null`.
- `/finish` возвращает `{workout, week?}`: ключа `week` может не быть.

## 5. Решение по TS-типам (SPEC §20.2)

**Типы и схемы валидации пишутся руками в `Web/api/`, а не генерируются.**
Генератор из `FitAPI` невозможен по построению: DTO объявлены с ручными
`CodingKeys` и схемы, читаемой рефлексией, не несут.

Источник правды — `Packages/FitAPI`. Связь с ним — тест, а не договорённость:

1. Swift-тесты `FitAPI` выгружают **эталонные JSON** на каждое тело §20.3
   (успешные ответы, конверт ошибки, причина `{code, params, message}`, карта
   дерева §20.9).
2. TS-тест в `Web/` прогоняет эталоны через написанные руками типы и схемы
   валидации. Расхождение — падение теста.

Следствия:

- Правка DTO в `FitAPI` без правки эталона не проходит в `FitAPI`; правка
  эталона без правки типов не проходит в `Web/`.
- Любой ответ сервера разбирается через схему валидации на границе `api/`, а не
  через `as SomeType`. Неизвестное значение закрытого словаря (`kind`, `code`)
  — отдельное, видимое состояние, а не молчаливый `undefined`.
- Строки, которые видит пользовательница, приезжают с сервера: каталога
  формулировок во фронтенде нет.
- Поле, которого нет в эталоне, в типах не появляется. Новое поле — сначала
  эталон и DTO, потом тип.

Каталог эталонов и способ его выгрузки (команда, место в `Packages/FitAPI`)
задаются при первом срезе, которому они нужны (срез 1 берёт `TodayCard`,
`Profile`, `WeekPlanResponse`, конверт ошибки), и **записываются сюда**.

## 6. Порядок срезов

Каждый срез проходит через весь путь — от экрана до живой базы, — а не
закрывает слой. Нумерация — порядок работы, не этапы SPEC (§17): срезы 1–6
покрывают В1 и В2, растяжка и прогресс (В3) и готовность к запуску (В4) идут
после, отдельными срезами.

| Срез | Что проходит | Чего в нём нет |
|---|---|---|
| **1. Сквозной минимум** | Каркас `Web/`, анонимный вход, `GET /v1/today` с `date`/`tz`, показ состава тренировки (`day.session`) с названиями из `/v1/content/exercises`. Данные подготавливаются кнопкой только в dev-сборке: `PATCH /v1/profile` (четыре поля), строка `equipment_profiles` с `is_default`, `POST /v1/week-plans`. Одна e2e-проверка | «Начать», линковка, реальный онбординг |
| **2. Линковка и старт** | Magic link, `unlinked_account` → экран линковки, `POST /v1/workouts`, `GET /v1/workouts/{id}` | Логирование подходов |
| **3. Экран упражнения** | Дерево §20.9, `POST …/sets` с клиентским `id`, таймер отдыха, Wake Lock, явное состояние обрыва сети | Замена, флаг боли |
| **4. Завершение** | `POST …/finish`, сводка, «План обновлён» | Заминка (В3) |
| **5. Онбординг** | Все экраны §5: профиль через `PATCH`, прямые записи PAR-Q, инвентаря, ограничений, цикла; dev-кнопка из среза 1 удаляется | — |
| **6. Сегодня целиком** | Чек-ин, оверрайды, лента недели, `/rebuild` после прямых записей, замена и флаг боли (`/alternatives`, `/substitute`), профиль | Растяжка, прогресс |

## 7. Как проверять

Три уровня, и ни один не заменяет другой.

1. **Vitest (юнит и контракт).** Схемы валидации против эталонных JSON (§5);
   чистые функции: выбор ветки дерева по карте, формирование пары `date`/`tz`,
   расчёт абсолютной метки таймера и множителя отдыха, разбор конверта ошибки.
   Компоненты — через Testing Library, на фикстурах, без сети.
2. **Playwright против локальных Supabase и Server.** Настоящий анонимный
   пользователь, настоящий JWT, настоящий `/v1`. Мок сервера здесь не
   используется: тест, который проверяет клиент на ответе, которого сервер
   отдать не умеет, ничего не доказывает.
3. **Руками на телефоне и в зале** — этап В4 (§17). Экран тренировки за столом
   не проверить.

### Локальная среда

Порядок как в `Server/Tests/FitServerTests/LiveHarness.swift`:

```bash
supabase start && supabase migration up --local
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" \
  -c "alter role fitserver with password 'fitserver'"
```

Сервер: `FITTRACK_ISSUER=http://127.0.0.1:54321/auth/v1`,
`FITTRACK_DB_PASSWORD=fitserver`, `FITTRACK_DB_PORT=54322` (умолчание сервера —
5432, а локальный Supabase слушает 54322), `FITTRACK_DB_TLS=disable`, затем
`swift run fitserver` из `Server/` (слушает `127.0.0.1:8080`). Ключ для supabase-js — из
`supabase status`.

Что знать об этой среде:

- После `supabase db reset` пароль роли `fitserver` нужно задать заново.
- Локальный Postgres упирается в 100 соединений, если контейнер аналитики
  застрял; симптом — `signup 500: Database error creating anonymous user`.
  Лечится `supabase stop` / `supabase start`.
- Vite слушает `127.0.0.1:5173` (`WEB_PORT` переопределяет). `site_url` и
  `additional_redirect_urls` в `Supabase/config.toml` пока указывают на
  `127.0.0.1:3000`; их приведение к 5173 — первый коммит среза 2, и redirect
  magic link должен с ними согласовываться.
- Письма magic link локально видны в Mailpit (`http://127.0.0.1:54324`);
  сквозной тест читает письмо оттуда через его API.
- Живые тесты `Server/`, которые стартуют тренировку, создают привязанных
  пользователей через Auth Admin API и требуют `FITTRACK_SERVICE_ROLE_KEY`
  (`supabase status -o env`, `SERVICE_ROLE_KEY`); ключ меняется при каждом
  `supabase start`.
- Живые тесты `Server/` перед слиянием среза гоняются одной командой из корня:
  `Server/scripts/live-tests.sh`. Она поднимает Supabase, задаёт пароль
  `fitserver`, берёт свежие ключи, при упоре в соединения один раз
  перезапускает Supabase и запускает `swift test` с `FITTRACK_REQUIRE_LIVE=1`:
  пропущенный живой тест в этом режиме — падение, а не зелёный прогон
  (подробно — `server-domain` §4 п. 4). Голый `swift test` без переменных
  зелёный и о сервере ничего не говорит.

## 8. Визуальные решения и дизайн-токены (приняты)

Визуальные решения принимает пользователь; здесь они записаны. Принято
направление D: структура светлого варианта, цвета тёмного. Новое визуальное
решение (цвет, размер, начертание, новый тип компонента) — снова к
пользователю, а потом сюда и в `tokens.json`.

### Правило: цвета и размеры — только из токенов

- В рукописном CSS (`Web/src/styles/app.css` и любой другой `.css`, кроме
  сгенерированного `tokens.css`) нет литералов цвета (`#…`, `rgb(…)`, `hsl(…)`)
  и размера (`px`, `rem`, `em`, `pt`, `vh`, `vw`): только `var(--…)`. Голые
  числа без единиц (`flex: 1`, `line-height` из токена) и проценты допустимы.
- В компонентах нет `style={…}`: вид задаётся классами из `app.css`.
- Нужен размер или цвет, которого нет, — сначала токен в `tokens.json`
  (с пометкой `derived`, если пользователь его не задавал), потом стиль.
- Проверяет `Web/src/styles/tokens.test.ts`; там же проверка контраста каждой
  пары «текст на фоне» из `app.css` — не ниже 4.5:1. Новая пара текста и фона
  в стилях — новая строка в `TEXT_PAIRS`.

### Источник и генератор

- Источник — `Tools/design-tokens/tokens.json`, формат W3C Design Tokens
  (DTCG): `$type` наследуется группой, ссылки `{group.token}`, размеры —
  `{value, unit}`, типографика — составной токен. Значения, выведенные при
  реализации, а не заданные решением, помечены
  `$extensions.fittrack.origin = "derived"`.
- `lib/tokens.mjs` разбирает формат один раз в плоский список (путь, тип,
  значение без ссылок); каждая цель лежит в `targets/` и получает уже его.
  Сейчас цель одна — `targets/css.mjs`. Вывод для Swift добавляется файлом
  `targets/swift.mjs` и записью в `TARGETS` в `build.mjs`; формат токенов для
  него не меняется.
- `build.mjs` пишет `Web/src/styles/tokens.css` (`npm run tokens` в `Web/`),
  `--check` только сверяет. Файл коммитится; тест падает, если он устарел, —
  тот же договор, что у `Contract/fixtures`.
- Имена CSS-переменных — путь через дефис (`color.text-muted` →
  `--color-text-muted`); типографика раскладывается на
  `--type-<имя>-family|size|weight|tracking|leading`.

## 9. Где `implement-feature` не подходит для Web как есть

1. **§1 п. 1 — doc-комментарий модуля.** У `Web/` его нет. Источник
   архитектуры — §20 (в первую очередь §20.2, §20.3, §20.9–§20.12) и этот файл.
   Описание структуры (README в `Web/`) пишется **первым артефактом** среза 1,
   до кода.
2. **§2 — граф зависимостей FitCore.** `Web/` в него не входит. Проверять перед
   срезом нужно другое: сервер и Supabase поднимаются локально (§7), нужные пути
   `/v1` существуют и покрыты тестами `Server/`, эталонные JSON нужного тела
   выгружены.
3. **§5 и чек-лист — «на каждый сценарий §18 тест».** Обязательные тесты веба —
   §20.15, но почти все они серверные (20a–20l). Для фронтенда обязательный
   минимум свой: контрактный тест эталонов (§5) на каждое тело, которое срез
   читает, и e2e на путь среза.
4. **§5 «`swift test` пройден».** Для `Web/` это `npm test` (Vitest), проверка
   типов (`tsc --noEmit`), линтер и Playwright, а не `swift test`.
5. **Расхождения SPEC и сервера.** Если фронтенд упирается в то, что SPEC не
   описывает или описывает иначе, чем отдаёт сервер, это решается по процедуре
   `server-domain` §1: остановиться, показать пользователю простым текстом в
   чате варианты и их последствия (без диалога и без заранее выбранного), внести
   решение в SPEC отдельным коммитом, потом писать код. Клиентская правка не
   должна молча «обходить» серверное поведение.

## 10. Остальное — по implement-feature

Ветка от чистого `master` (`feature/web-<срез>`), стиль коммита (императив,
английский заголовок, тело с обоснованием нетривиальных решений), правило
«несостыковки фиксировать и называть пользователю» — из
[implement-feature](../implement-feature/SKILL.md) без изменений. Серверные
правки, которые срезу понадобились, идут отдельным коммитом и по
